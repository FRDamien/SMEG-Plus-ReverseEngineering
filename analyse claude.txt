Comment fonctionne l’ensemble
L’architecture. C’est un système embarqué VxWorks 6.7 (temps réel, de Wind River) sur un processeur PowerPC big-endian. Le vxWorks.bin n’est pas un simple exécutable ELF, c’est une image monolithique : le noyau, les pilotes (BSP = Board Support Package), la pile réseau Interpeak et toutes les applications métier (interface, audio, navigation, Bluetooth) sont liés ensemble en un seul blob chargé en flash à l’adresse 0x720000.

Le processus de flash. Le flasher.inf indique au bootloader quoi écrire et où. dbsystem.bin est une base de données système minuscule (40 octets) qui accompagne l’image. Au démarrage, l’unité cherche /bd0/SMEG_PLUS_UPG/upgrade.out sur la clé USB (c’est le bd0, block device 0) pour lancer la séquence de mise à jour.

Le découpage matériel. Les chaînes montrent que la même image gère plusieurs variantes (PTC/PTC2/PTC3, avec ou sans nav, avec ou sans BT, « Monozukury » A/B/D/H). Le firmware détecte donc le matériel au boot et active les bons modules.

La chaîne de checksums que tu dois comprendre
C’est le cœur du problème. Si tu modifies un seul octet de vxWorks.bin, tu casses cinq contrôles en cascade :

vxWorks.bin  ──CRC──►  (1) octet 8 de dbsystem.bin
                       (2) vxWorks_bin.inf  (CRC32: 1898196070)
                       (3) flasher.inf      (ligne vxWorks.bin ... 71242c66)

dbsystem.bin ──CRC──►  (4) offset 36 (auto-CRC des 36 premiers octets)
                       (5) flasher.inf      (ligne dbsystem.bin ... 215167f7)
                       dbsystem_bin.inf     (CRC32: 558983159)

flasher.inf  ──CRC──►  flasher.crc          (0x4A5FE7FE)
Autrement dit, pour qu’un patch soit accepté, il faut recalculer tous ces CRC dans le bon ordre, du plus interne vers le plus externe. C’est purement mécanique — un petit script Python le fait — mais si tu en oublies un, l’unité rejette l’image. C’est la raison n°1 des SMEG+ briqués lors de patches.

Pourquoi le telnet est la bonne piste
VxWorks embarque un shell cible (target shell) et le firmware contient bien le serveur telnet Interpeak (IPTELNETS, vu dans les chaînes). L’énorme avantage par rapport au patch :

Zéro recalcul de CRC — tu ne touches pas aux fichiers flash.
Zéro risque de brique — tes changements sont en RAM. Si tu te trompes, un simple redémarrage remet tout en place.
Expérimentation en direct — tu peux essayer plusieurs valeurs de buffer et écouter le résultat immédiatement.
Avec le shell VxWorks tu peux lire/écrire des variables globales, appeler des fonctions, inspecter la mémoire — exactement ce qu’il faut pour trouver et réduire ce tampon.

Mais il y a deux « si » que je ne peux pas lever avec ces seuls fichiers :

L’accès physique. Le shell telnet passe par l’interface Ethernet de l’unité. Format bigquick c'est quoi ?

Excellent ! Résultat capital. 9421ffe0 7c0802a6 — c’est exactement les mêmes premiers octets que vxWorks.bin. C’est du code PowerPC big-endian. Le contenu décompressé est 32 434 416 octets = 0x1EEE8F0 — exactement word[1] du record 0.

Voici la réponse complète à ta question :

Format BigQuick : démystifié
C’est un format maison Magneti Marelli, extrêmement simple :

Offset 0x0000 : Header Record 0 (28 octets)
                word[0] = 0x00010004  → version du format (1.4)
                word[1] = 0x01EEE8F0  → taille décompressée bloc 1 (32 Mo)
                word[2] = 0x01D646B0  → taille flash destination bloc 1
                word[3..6] = infos diverses
                word[7] = 0xDEADBEEF  → marqueur fin de record

Offset 0x0020 : Header Record 1 (idem, 2e bloc)
                word[1] = 0x00E86B00  → taille décompressée bloc 2 (15 Mo)
                ...

Offset 0x0040 → 0x07FF : Padding DEADBEEF

Offset 0x0800 : 1 octet de type (0x08)
Offset 0x0801 : Flux ZLIB standard (78 9C ...)
                → décompresse en 32 Mo de code PowerPC PPC
                → c'est l'application principale (audio, BT, UI...)
Ce n’est PAS du tout un format impénétrable. C’est juste :

Un petit header avec des métadonnées
Un seul octet de flag
Du zlib standard
Et la taille décompressée (0x1EEE8F0) est exactement dans le header record → recalculable automatiquement.

Ce que ça implique pour ton patch
python
# Pour patcher f_BigQuick.bin :
# 1. Décompresser le contenu zlib (offset 0x801)
# 2. Modifier les octets cibles dans les 32 Mo de code PPC
# 3. Recompresser en zlib
# 4. Réécrire le fichier : header + 0x08 + nouveau_zlib
# 5. Mettre à jour word[2] si la taille compressée change
# 6. Recalculer CRC32 → .inf + ctrl.bin
Aucune crypto, aucune signature asymétrique sur le contenu — juste du CRC32. C’est entièrement scriptable.
